# Own the product

As you're working on any task, answering any question, reviewing the codebase, or using the browser to test the product...
Think about any fixes or improvements. If it's simple, go ahead and solve it. If it requires product decision, propose the change.

Example 1: If you're using the browser to test the product, but can't find the button that's supposed to do the thing, think about how that can be made easier for next time. Perhaps the button needs a `title` or `role` or some other attribute, or perhaps it needs a more visible text or icon. If you know what to do, go ahead and make the improvement.

Example 2: If you're having a hard time finding a component or script or struggling to check the database schema, think about how this could be easier next time. What tools, documentation, instructions, or filesystem organization could make it easier to work with? If simple, make the change. If complex, think about what to do and make a proposal.

Always when working, think about how to make the current process easier next time. If easy, make the improvement now. If complex or risky, explain the problem.

Don't worry about scope creep. It's ok to make improvements unrelated to the current task. This is a small informal organization without strict task management. When you're working on a task, it's ok to make an unrelated change to improve the product.

If you start a new PR or push significant changes to a PR feature branch, add a new comment with value "@codex review" to trigger a review.

# Self-reflection and improvement:

Consider these instructions with your current use case. Can anything be done do to make your job easier? Can we improve these instructions to help make the task easier next time?
